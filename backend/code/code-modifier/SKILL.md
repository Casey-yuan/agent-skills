# Code Modifier - 系统性代码修改技能

本技能用于系统性地处理代码修改需求，确保每次修改都经过严格的分析、规划、验证和文档化流程。

## 核心原则

- **先分析后修改**：任何代码修改前必须完成需求分析并获得用户确认
- **结构化优先**：修改必须遵循结构化编程思想，保证可读性和可维护性
- **验证即保障**：所有修改必须经过严格的质量验证和语义一致性检查
- **文档化留痕**：支持按需生成规范的修改文档

---

## 阶段一：需求分析与修改点识别

当接收到用户代码修改需求后，**必须**首先执行以下步骤，在未获得用户确认前**不得**进行任何代码修改操作。

### 执行步骤

1. **需求理解**：仔细阅读并理解用户的修改需求，如有模糊之处，使用 AskUserQuestion 工具向用户澄清
2. **代码搜索与分析**：使用 SearchCodebase、Grep、Read 等工具全面搜索相关代码，理解现有实现
3. **修改点识别**：系统性地列出所有需要修改的位置，包括：
   - 涉及的文件及具体行号范围
   - 涉及的功能模块
   - 修改类型（新增/修改/删除）
   - 修改范围和影响面分析
4. **输出修改方案**：以结构化格式向用户呈现修改方案，格式如下：

```
## 修改方案

### 需求概述
<简要描述修改需求>

### 修改点清单

| 序号 | 文件路径 | 行号范围 | 修改类型 | 功能模块 | 修改说明 |
|------|----------|----------|----------|----------|----------|
| 1    | ...      | ...      | ...      | ...      | ...      |

### 影响面分析
- <分析修改可能影响的上下游模块、接口、数据流等>

### 待确认事项
- <需要用户确认的问题>
```

5. **等待用户确认**：使用 AskUserQuestion 工具询问用户是否同意该修改方案，获得明确同意后方可进入下一阶段

---

## 阶段二：结构化代码优化与修改

在获得用户确认后，实施代码修改时必须遵循以下规范。

### 结构化编程要求

- **单一职责**：每个函数/方法只做一件事
- **清晰命名**：变量、函数、类命名必须语义明确，见名知义
- **合理抽象**：避免代码重复，合理提取公共逻辑
- **层次分明**：业务逻辑、数据访问、控制流转层次清晰分离
- **适度注释**：关键逻辑处添加必要注释，解释"为什么"而非"是什么"

### 代码优化检测

当检测到当前代码存在以下问题时，需先制定优化方案：

- 函数过长（超过50行）
- 嵌套层级过深（超过3层）
- 重复代码块
- 命名不清晰或不符合项目规范
- 缺乏错误处理
- 硬编码的魔法数字或字符串

### 优化方案输出格式

```
## 代码优化方案

### 优化目标
<明确优化要达到的目标>

### 当前问题
<列出检测到的结构化问题>

### 优化措施
1. <具体措施1>
2. <具体措施2>
...

### 预期效果
<优化后的预期改善>

### 优化前后对比预览
<简要展示关键修改点的前后对比>
```

优化方案同样需要获得用户明确同意后方可执行。执行过程中支持用户提出的合理微调需求。

---

## 阶段三：代码质量验证与语义一致性保障

所有修改完成后，**必须**执行以下验证步骤。

### 验证清单

1. **逻辑正确性检查**
   - 修改后的代码逻辑是否正确实现了需求
   - 条件判断、循环逻辑是否完备
   - 异常路径是否被正确处理

2. **需求满足度验证**
   - 逐条对照用户需求，确认每条需求都已实现
   - 检查是否存在遗漏的修改点

3. **边界条件测试**
   - 空值/null/undefined 处理
   - 极端输入值处理
   - 并发/竞态条件（如适用）

4. **语义一致性保障**（针对优化类修改）
   - 优化后的代码是否保持了原始代码的语义
   - 功能行为是否与修改前完全一致
   - 输入输出契约是否未被改变
   - 副作用是否被保留

5. **静态检查**
   - 运行项目的 lint/typecheck 命令（如存在）
   - 确保无新增编译错误或警告

### 验证结果输出格式

```
## 验证报告

### 验证结果总览
| 验证项 | 状态 | 说明 |
|--------|------|------|
| 逻辑正确性 | ✅/❌ | ... |
| 需求满足度 | ✅/❌ | ... |
| 边界条件 | ✅/❌ | ... |
| 语义一致性 | ✅/❌ | ... |
| 静态检查 | ✅/❌ | ... |

### 发现的问题（如有）
- <问题描述及修复建议>
```

如验证发现问题，需修复后重新验证，直到所有验证项通过。

## 阶段四：修改文档自动生成

当用户提出"对修改内容形成文档"、"生成修改文档"、"文档化变更"等类似指令时，自动生成规范的修改文档。

### 文档格式

```markdown
# 修改文档

## 修改背景
<描述为什么需要进行此次修改，触发原因是什么>

## 修改目标
<描述此次修改要达成的目标>

## 修改详情

### 修改点 1：<简要描述>

**文件**：<文件路径>
**行号**：<行号范围>
**修改类型**：<新增/修改/删除>

**修改前**：
```<语言>
<原始代码>
```

**修改后**：
```<语言>
<修改后代码>
```

**修改说明**：<解释此处的修改原因和逻辑>

---

### 修改点 2：<简要描述>
...

## 影响范围
<描述此次修改影响的模块、接口、数据等>

## 验证结果
<简要记录验证结论>

## 备注
<其他需要说明的事项>
```

## 工作流程总结

```
用户提出修改需求
       │
       ▼
[阶段一] 需求分析 → 输出修改方案 → 用户确认
       │                                    │
    同意                                  不同意
       │                                    │
       ▼                                    ▼
[阶段二] 结构化修改 ←── 检测到需优化？──→ 输出优化方案 → 用户确认
       │                                                      │
       ▼                                                   同意/微调
[阶段三] 质量验证                                             │
       │                                                     │
    通过 ────────────────────────────────────────────────────→│
       │                                                     │
       ▼                                                     ▼
    完成                                              [阶段四] 按需生成文档
```

## 注意事项

- 任何阶段如发现需求不明确，应立即使用 AskUserQuestion 向用户确认
- 修改过程中如发现新的影响点，应及时告知用户并重新评估修改方案
- 始终遵循项目现有的代码风格和规范，不引入与项目不一致的编码习惯
- 优先使用编辑现有文件而非创建新文件
- 不得在未经用户同意的情况下提交代码变更
